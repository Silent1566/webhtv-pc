# ADR 0013 弹幕自带渲染时钟（逐帧插值 + 只重绘不重建）

状态：接受（已落地）。日期：2026-11-22。

## 背景

用户 2026-11-22 反馈：弹幕默认速度太快、可选时长太短（想要长的档位或自己填），
而且「现在的弹幕看着不够流畅、卡卡的，文字看着也像是有拖影」。

当时的实现与这条观感的对应关系：

- **位置是离散事件**：叠加层直接读 `_controller.position`（`ui/player_page.dart:4270`），
  那是 media-kit `stream.position`（libmpv `time-pos` property-change）的最近一次上报。
  两次上报之间页面不重建，弹幕就停在原地；上报一到又整段跳过去——慢速弹幕上最明显。
- **每次上报重建整页**：`_onControllerChanged` 里 `setState(() {})`
  （`ui/player_page.dart:1008-1031`），弹幕叠加层的刷新率因此绑死在位置上报节奏上，
  整页重建本身也在抢同一帧的预算。
- **每帧重排全表**：`DanmakuTrackAllocator.visibleAt` 每次调用都排序并重算全部轨道
  （`lib/core/danmaku.dart`），一集几千条弹幕时是每帧 O(n log n)。
- **每条每帧 7 次文本排版**：`DanmakuPainter` 为正文排一次版，再为 6 个描边方向各排
  一次，最后一共画 7 遍文字。本机实测（34 条可见弹幕、1920×1080 表面、Ahem 字体下界）
  每帧 6.9ms，占 16.7ms 单帧预算的四成。
- **描边是「6 个方向各叠一遍黑字」**：偏移量落在半像素上，字边出现柔化的双边与外圈
  虚光——这正是用户说的「拖影」。描边之外的正文还画了两遍。

## 决策

1. **叠加层自带渲染时钟**：新增 [DanmakuMotionClock]（`lib/core/danmaku_motion.dart`），
   把播放器上报的离散位置按墙钟插值成每帧连续位置。三条边界写死并单测：
   暂停不动、拖动/切集立即跟随（容差 120ms 内的上报抖动不回退）、上报断流最多外插
   600ms（缓冲卡住时不让弹幕飞出画面半天才对上）。
2. **逐帧重绘但不重建**：叠加层用 `Ticker` 驱动一个 `ValueNotifier` 作为
   `CustomPaint` 的 `repaint` 通道，外层层包 `RepaintBoundary`。
   逐帧推进只重绘这一层，不 `setState`，不重建播放器页。
3. **场景预排**：新增 `DanmakuScene`，轨道只排一次，查询用开始时刻二分出活动窗口。
   `DanmakuTrackAllocator.visibleAt` 改为「建场景 + 查询」的兼容包装，语义逐条不变
   （`test/danmaku_scene_test.dart` 用多尺寸/多时长与旧实现逐条比对）。
4. **排版缓存 + 真描边**：文本排版按「文本 + 字号 + 颜色 + 描边」缓存（上限 512 条，
   超出整体清空）；描边改成一次 `PaintingStyle.stroke`，不再叠 6 份文字。
5. **播放器只交事实**：叠加层接收「最近一次上报位置 + 播放状态 + 倍速」，
   暂停时 `playing=false` 直接停在原地；直播弹幕不再靠页面 250ms 的定时器推进，
   改由叠加层每帧取墙钟。
6. **默认放慢、档位加长、可自定义**：`scrollDurationMs` 默认 8000 → 12000，
   夹取上限 20000 → 60000；设置页档位 6–60s，末尾「自定义…」支持 2..60 秒。

## 后果

- 弹幕位移变成每帧连续：12s、1920 宽的画面里，16ms 一帧约 1.2px，
  与旧实现「每 250ms 跳 18px」的观感差异就是用户所说的「流畅」。
- 每帧绘制从 6.9ms 降到 0.46ms（同上测量口径），播放器页不再为弹幕增加重建。
- 暂停、拖动进度条、切集、倍速的行为由 `DanmakuMotionClock` 单点决定（8 个单测），
  不再隐含在「上报有多频繁」里。
- 位置上报彻底断流时最多外插 600ms，之后停在原地等下一次上报；恢复时会重新对表，
  幅度超过 120ms 的跳变按 seek 处理（这正是拖动进度条应有的行为）。
- 默认从 8s 放慢到 12s 之后，同一条轨道被占用的时间更长，同屏条数会略少；
  这是现有「轨道窗口内独占」模型的直接结果，也是放慢速度的代价。

## 实测（2026-11-22 21:13–21:18，本机环境）

方法：`flutter build linux --profile`（本仓库 sysroot 环境）+ 一个临时探针
（`SchedulerBinding.addTimingsCallback` 每 2 秒汇总 build/raster 的 p50/p95 与掉帧，
并记录该窗口内每次绘制画了多少条弹幕），测完即删除；原始日志留在
`.local/frame-probe/run.log`（未入库）。

这套环境决定了那些数字的绝对量级：

- QEMU 虚拟显卡 `bochs-drm`（PCI `1234:1111`），**没有任何 render node**
  （只有 `/dev/dri/card0`，无 `renderD*`）⇒ 不存在硬件 GL：
  应用侧 `libEGL: DRI3 error` → Impeller 走软件 GL；
  视频侧 `media_kit: VideoOutput: S/W rendering.`。
- 输出 1920×1080@59.96Hz；4.4GB 内存已用 3GB，两个 swap 分区基本吃满，
  loadavg 10.9/10 核。

只取「整窗都是弹幕开」与「整窗都是弹幕关」的窗口（各 71 / 60 个窗口、3918 / 2895 帧）：

| 场景 | fps（中位） | build p50 | raster p50 | raster p95 | raster 超 16.7ms | 每帧可见弹幕 |
| --- | --- | --- | --- | --- | --- | --- |
| 弹幕开 | 28.3 | 3.55ms | 11.15ms | 30.27ms | 36% | 16.9 条 |
| 弹幕关 | 25.6 | 2.76ms | 7.24ms | 26.07ms | 24% | 0 |

结论：

- 弹幕层在这台机器上约 **3.9ms/帧**（17 条 ≈ 0.23ms/条），约合 raster 的三分之一。
- **关掉弹幕帧率反而更低**：此时帧只来自 25fps 的视频更新（约 26fps），而弹幕开着时
  渲染时钟会额外请求帧（28fps）。所以弹幕不是帧率上限的成因，上限是软件光栅。
- Dart 侧（build）从来不是瓶颈：p50 2.8–3.6ms，远低于 16.7ms 预算。
- 「每帧约 1.2px 的连续位移」在有 GPU 的机器上才是完整观感；本机只能以 ~28Hz
  采样呈现，但仍比改前「等位置上报到达才跳一格」连续得多。

## 被否决的替代方案

| 方案 | 否决理由 |
|---|---|
| 让 `player_page` 自己跑 60Hz `setState` 驱动弹幕 | 整页重建（seek 条、进度、菜单…）每帧一次，代价比省下的流畅度更高 |
| 每条弹幕一个 `AnimationController` | 屏幕上几十条弹幕就是几十个 ticker，且弹幕出现/消失时要频繁增删控制器 |
| 保留 `visibleAt` 的整表重排在渲染层，只缩小查询窗口 | 每帧仍要排序全表；预排一次能省掉，且语义可逐条比对 |
| 用 `MaskFilter.blur` 的阴影代替描边 | blur 比 stroke 更贵，视觉上也更糊，与「拖影」的诉求相反 |
| 直接降到 30Hz 重绘 | 仍然与上报节奏解耦，但省不下多少；而且 30Hz 的高速移动弹幕更容易被看成抖动 |
| 把速度档位做成滑块（连续值） | 档位明确可读、可复现；真要特殊值，自定义输入已经覆盖 |
