# ADR 0012 启动后台增量刷新配置（本地缓存先顶上，网络回来再换）

状态：接受（已落地）。日期：2026-11-22。

## 背景

用户 2026-11-22 提出：每次启动应用应该自动刷新各个配置；异步就行；最好增量——
远端拉取失败时，本地的缓存和已经编译/注册好的站源还应该能继续用；如果增量不好
做，退一步做异步全量也能接受。

当时的实现与这条诉求的差距：

- `AppState.bootstrap()` 只从数据库**恢复**最后一份配置（`_configs = listConfigs()`
  那一段），不核对来源有没有更新；`configs.updated_at` 只在用户手动刷新或导入时前进。
- 刷新能力其实已经在：`refreshConfigRecord` / `refreshAllConfigs` 与配置页的
  「刷新 / 全部刷新」按钮，但只在用户点下去时才发生。
- 猫源 bundle 早已是增量的先例：`CatBundle.ensure` 只拉 32 字节的 `index.js.md5`
  比对，命中就用本地缓存（`cat_bundle.dart:1-11`）。
- `DESIGN.md:533` 对 AI 推荐行写的是同一套语义：「进页面先只读缓存，输入指纹不一致
  或过期才后台刷新一次；刷新失败保留旧内容」。本次不是发明新语义，是把它用到配置
  来源上。

## 决策

1. **时机**：应用壳层首帧之后（`ui/app.dart` 的 post-frame）以 `unawaited` 发起；
   `bootstrap()` 仍然只同步恢复本地缓存，不为网络等待。同一进程只跑一轮
   （`startupConfigRefresh()` 记忆 Future），壳层重建不会重复打网络。
2. **范围**：`configs` 里能自己刷新的来源（HTTP(S)、本地文件；仓库记录按存下来的
   `repositoryIndex` 展开，而不是「永远第一项」）。排除三类，各有硬理由：
   - 猫源 bundle：内容由本机 Node 现场生成，`CatNodeRuntime.start()` 第一步就是
     `await stop()`（`cat_runtime.dart:118`）——启动时刷它会把正在服务当前配置的
     进程和端口一起换掉，等于打断用户正在用的站点；它的新鲜度由启动恢复/激活时的
     bundle md5 比对负责。
   - 安卓桥接源：内容在设备上，启动恢复路径（`_restoreLastConfig`）已经按记忆精确
     重拉过一次；设备离线时后台再打一轮只会产出一堆无意义失败。
   - 粘贴的 JSON 文本：`origin` 是 `inline://json`，没有可刷新的来源。
3. **增量**：两段判据，先便宜后贵。
   - 条件请求：把上一轮响应的 `ETag`/`Last-Modified` 落库（`configs.etag`、
     `last_modified`），下一轮发 `If-None-Match`/`If-Modified-Since`；`304` 直接
     当「没变」，连响应体都不读、也不解析。`304` 是**一等结果**
     （`FetchedConfigText.notModified`），不是错误。
   - 内容摘要：服务端没给校验值时，按「解析 → toJson」归一化后的 SHA-256
     （`configRecordContentHash` ↔ `configs.content_hash`）比对；一致则只记检查时间。
   两条都没命中才写库（`refreshConfigContent` + `saveConfigSites`），
   `updated_at` 只在这一步前进。
4. **失败不覆盖**：远端拉不下来只写 `last_checked_at` / `last_check_error`，
   内容、站点数与 `updated_at` 一律不动——本地缓存与已注册/已编译的站源继续照常
   可用。失败**静默**：进日志与记录，不写全局 `lastError`（那是用户动作的错误位）。
5. **生效时机**：内容真的变了才考虑换内存配置。用户还停在启动后的首页（没打开详情、
   没进分类）→ 立即换新并刷新首页；已经走进详情/分类 → 只更新本地库，下次切换配置
   或重启生效，绝不把正在看的页面连根拔掉。
6. **可见性**：不弹窗、不弹提示条。配置页每行第二行摘要显示「检查失败：<原因>」或
   「N 分钟前检查过」，与既有的站点/直播/更新时间同一行。
7. **手动刷新不变**：点「刷新 / 全部刷新」仍然是整份重拉并重写（`updated_at` 前进），
   语义是「我现在就要它是最新的」。两条路径共用同一个落库入口，但手动路径不发条件
   请求。
8. **存储**：schema 11 → 12 加法式加五列（`etag`、`last_modified`、`content_hash`、
   `last_checked_at`、`last_check_error`），并按现有内容回填 `content_hash`——否则
   升级后第一次启动会把每条配置都当成「内容变了」集体重写一遍。

## 后果

- 启动不再无条件信任库里的配置，但首屏仍然只读本地缓存：网络更新最晚几秒后到，
  到不了也不影响使用。
- 配置列表的「更新」时间从此只表达内容变化；「检查时间」是另一个量
  （`last_checked_at`）。两者混用会让列表看起来每次启动都在变。
- 每次启动会为每条可刷新配置发一个请求（多数是几十字节的 `304`）；串行执行，
  失败互不影响。
- 猫源/桥接源的用户看不到检查时间：它们的新鲜度由各自路径决定，列出来反而会让人
  以为后台没跑。

## 被否决的替代方案

| 方案 | 否决理由 |
|---|---|
| 每次启动全量重拉（不做增量） | 用户明确要增量；且全量会把「内容没变」写成「内容变了」，配置列表的更新时间每次启动都跳一次，当前配置还会在启动瞬间重拉首页 |
| 定时轮询（每小时/每天） | 用户要的是「每次启动」；桌面端定时器还要处理休眠与待机，收益不抵复杂度 |
| 猫源也纳入本轮 | `CatNodeRuntime.start()` 会先 `stop()` 掉正在服务的运行时，端口随之变化——直接打断当前正在用的站点 |
| 桥接源也纳入本轮 | 与启动恢复重复；设备离线时每台设备都要等一轮超时，产出全是失败 |
| 内容变了就立即换（不看用户走到哪） | 会收起正在看的详情页、清零分类翻页位置；用户对「后台动作改变我正在看的页面」没有容忍度 |
| 用提示条报告后台更新 | 用户选的是「静默 + 配置页显示检查情况」；启动时弹一条与启动无关的提示，等于用通知换配置页一行摘要 |
| 只做摘要、不做条件请求 | 服务端给了 `ETag` 时能省掉整份下载（配置可达数百 KB），多存两列的代价明显更小 |
