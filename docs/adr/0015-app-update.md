# ADR 0015 应用本体更新：手动检查、可选自动检查与在线安装

状态：接受（已落地）。日期：2026-11-23。

## 背景

用户 2026-11-23 提出：支持手动检查更新，允许打开开关自动检查更新，最好能支持在线
更新功能。

落地前的事实（都在仓库里有据可查）：

- `docs/release/windows.md` 与 `.github/workflows/desktop-release.yml` 都显式写着
  「无自动更新」：更新需要签名通道与 ADR（`docs/phase9/README.md` P2-7）；
- 发行形态是 Windows 便携 zip 与 Linux AppImage + deb，用户数据在 `%APPDATA%` /
  `~/.local/share` 一侧，替换程序目录本身不影响数据；
- 版本名唯一来源是 `pubspec.yaml` 的 `version:`，而**同一个版本名会被反复发版**：
  发布 tag 形如 `v0.1.0-202611231630` / `v0.1.0-beta-202611231630`，只有时间戳
  区分先后。因此「版本名更大」不是唯一的「更新」判据；
- 每个 Release 都带 `SHA256SUMS.txt`，Windows 侧签名是可选步骤（当前未配置）。

## 决策

1. **数据来源**（ADR-0015 修订）：优先级是
   **固定静态索引 → 配置的 GitHub 下载代理 → Releases API 一次**。
   - 索引：CI 从真实发布事实自动生成 `releases.json`，发布到固定 prerelease tag
     `update-channel`（`.../releases/download/update-channel/releases.json`）。
     客户端读到的就是与 API 同构的发布列表，因此版本比较、通道筛选不变。
   - 缓存：成功响应连同 ETag / Last-Modified 与 UTC 时间落盘；条件请求 `304`
     复用缓存，冷启动可直接用缓存；离线时保留旧结论但标为**缓存**且不允许安装。
   - 兜底：静态源失败才查一次 API；`403/429` 区分「有额度证据的限流」与普通
     forbidden，记录 `retryAt` 冷却窗口，冷却期内不再打 API（静态源仍可尝试）。
   - 两个通道：稳定版只取非 prerelease、tag 不带 `-beta-` 的发布；测试版取全部
     非草稿发布。通道里按「版本名 → tag 构建时间戳」取最新的一条。
   - 首次发版尚未生成索引时，走同一套 API 兜底，不把索引缺失当成「已是最新」。
2. **本机身份**：版本名（`appVersion`）+ CI 注入的发布 tag（`--dart-define=APP_TAG=`）。
   本地构建 tag 为空 = **开发构建**：不参与通道比较，只展示最新发布供手动下载。
3. **更新判据**（`core/app_update.dart` 的 `AppRelease.isNewerThan`）：
   - 版本名更大 → 更新；
   - 版本名相同 → tag 构建时间戳更晚才算更新；
   - 版本名更旧 → 永远不算更新（时间戳再新也不能盖过版本名）；
   - 草稿不参与。
4. **手动检查**：设置 → 维护 → 软件更新。检查不阻塞界面、可重试；失败显示原因
   （限流 / 404 / 超时 / 响应不可解析），不把失败伪装成「已是最新」。
5. **自动检查**：默认**关闭**，开关写入 `settings.json` 的 `update` 段
   （`SettingsWriter.update` 独占临时名）。启动后壳层首帧之后异步触发一次，
   `24` 小时内最多一次；**只检查，不下载、不安装**。打开开关的瞬间立刻查一次
   （用户拨开关就是「现在给我看看」）。
6. **可见性**：自动检查发现新版本 → 一条右下角通知（带「查看」动作直达更新页），
   每个 tag 只提示一次；设置行的副标题与更新页常驻显示最近一次的结论。失败只写
   日志与页面，不弹错误提示条。
7. **下载与校验**（ADR-0015 修订）：只从该 Release 的资产下载；默认经公开
   GitHub 下载代理加速（缺省 `https://gh-proxy.com/`，可关闭、切换
   `https://ghfast.top/` 或填自定义 HTTPS 前缀），代理失败自动回退直连。
   **只重写本项目公开 Release 的 `github.com/.../releases/download/...` 地址**：
   API、其它仓库与带凭据的地址一律直连，代理不接收 Cookie/Authorization。
   第三方代理会看到公开下载 URL，速度因网络而异，页面如实说明。
   **必须有 SHA-256**（API 的
   `digest` 优先，否则读 `SHA256SUMS.txt`）。校验不通过删除半成品并报错；
   发布没有给校验值时拒绝下载安装。
8. **安装三条路**（全部由用户点击触发，从不静默替换正在运行的程序）：
   - **Linux AppImage**（运行时存在 `APPIMAGE` 环境变量）：下载 → 校验 →
     同目录暂存 → `chmod 755` → 旧文件改名为 `<路径>.old` → 原子改名换入。
     任一步失败回滚，失败不留下半成品。**不自动重启**：新旧两个实例同时跑会
     重复占用 sidecar / 代理端口 / 数据库。
   - **Windows 便携 zip**：下载 → 校验 → 在更新目录写 PowerShell 换装脚本
     （放在安装目录之外，不会把自己换掉）→ detached 启动脚本。脚本等本进程退出
     （最多 10 分钟）→ 用 `tar.exe`（缺省回退 `Expand-Archive`）解包 → 校验
     `webhtv_pc.exe` → 安装目录改名为 `<安装目录>.webhtv-old` → payload 移入
     原位 → 启动新版本；任一步失败还原旧目录。日志落在
     `<cache>/updates/<tag>/update.log`。
   - **deb 等其它形态**：只下载，提示用系统安装器完成（deb 需要包管理器权限，
     应用不自动提权）。
9. **不做静默自动安装**：现在没有代码签名通道，SHA-256 只证明「文件没被替换」，
   不证明「发布者是谁」。把自动安装设成默认行为等于把这个缺口变成默认行为，
   所以自动模式只到「检查」为止。
10. **不越界**：不检查/不更新站源（设计文档 §22.3「自动更新只更新应用」），
    不做增量更新与后台预下载，不改用户数据目录。

## 后果与限制

- 发布流水线必须注入 `APP_TAG`（`desktop-release.yml` 的 Windows / Linux 两个
  构建步骤）。**在这次改动之前发布的旧包没有 `APP_TAG`**：它们升级上来后会把
  自己当成开发构建，需要手动下载一次新包，之后才进入正常更新通道。
- 同名版本靠 tag 时间戳比较；不符合
  `v<version>[-beta]-yyyyMMddHHmm` 形态的手工 Release 会被发布索引与客户端一起
  忽略（不参与比较，也不会被误判成更新）。
- Windows 换装脚本无法在 CI/开发机上端到端验证：单测锁的是脚本关键步骤与参数
  （pid、安装目录、改名/移入/启动/回滚）与三条安装结局，真机首次使用需要人工验收。
- 便携包若解压到受保护目录（例如 Program Files）：换装脚本的目录改名会失败，
  脚本会保留原目录并退出，日志在 `<cache>/updates/<tag>/update.log` 里可读；
  应用不会尝试提权。
- GitHub 未认证限流 60 次/小时/IP：自动检查 24 小时一次 + 手动检查远低于上限；
  但同一出口 IP 的其它请求会共用这份额度（实测本机曾 `remaining=0`）。改走
  静态索引后，常规检查不再依赖这份共享额度；API 只剩失败兜底，并尊重
  `Retry-After` / `x-ratelimit-reset` 冷却。
- 下载代理是第三方服务，不保证更快或可用：本机对一个 Windows 资产的前 1 MiB
  采样中 gh-proxy 约 0.76 MiB/s、直连约 0.35 MiB/s、ghfast 约 0.30 MiB/s（单次
  冷启动，不能外推）；三路片段内容一致，但整包仍以 SHA-256 为准。因此代理失败
  必须回退直连，代理结果也要过完整包校验。
- 静态索引只在发布流水线成功发包后更新；流水线改动合并后的**下一次**发布才产生
  第一个真实索引。此前版本用 API 兜底，不会误判。
- 后续项：引入代码签名（Windows Authenticode / Linux minisign）并在安装前验签，
  之后才考虑「下载完成后自动安装」。

## 备选与不采纳

- **人手维护第二份更新清单**：清单由 CI 从真实发布事实自动生成，不接受手工维护
  的版本源。这是对原「不另维护清单」取舍的修订：不再让常规检查消耗共享匿名
  API 额度（见「后果与限制」）。
- **早期方案：直接依赖 GitHub Releases API**（本 ADR 原决策）：匿名额度被同出口
  IP 其它请求耗尽时，一天查一次也会 403；保留为失败兜底而不是主路径。
- **旧备选：在仓库里再维护一份 `latest.json` 更新清单**：GitHub Releases 已经带资产、
  tag 与校验文件，多一份清单就多一处会漂移的事实。
- **直接覆盖 Windows 运行目录里的文件**：正在运行的 exe/dll 覆盖不可靠，且没有回滚。
- **deb 自动安装（pkexec/dpkg）**：需要交互式提权，超出应用边界。
- **按「发布时间」判断新旧**：发布可以重跑到旧 commit，tag 的构建时间才是可比较的事实。
