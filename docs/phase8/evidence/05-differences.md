# 证据 05 · 与上游的有意差异（9 条）

`design/05-test-and-acceptance.md` §7 要求这 9 条**逐条留痕**，
理由是：本轮改造参考了安卓版「默影视」，但**不是逐项照搬**。
不写清楚，后来者会把"参考"读成"对齐"，然后把 PC 端做对的地方改回去。

上游仓库：`F:\Workspace\webtv4\webhtv`（Android 工程「默影视」）。

---

| # | 差异 | 上游做法 | PC 端做法 | 为什么 PC 端这样做 |
| --- | --- | --- | --- | --- |
| 1 | 时钟默认值 | `display_time` 默认 **false** | 默认 **true** | PC 是"坐在电脑前"的场景；全屏播放时任务栏不可见，时钟是真实需求。上游是手机/电视场景，系统状态栏常驻，时钟重复。（用户 2026-10-18 确认） |
| 2 | 网速屏显 | `PlaybackSpeedMeter` 按秒采样真实字节吞吐 | **Phase 8 当时：不实现**，开关存在但**置灰**；**后续已实现**（双数据源：`demuxer-cache-state` 内解析 `raw-input-rate` 字段，解析不到回退 `cache-speed`，见下方「更正 2」） | **当时**的理由：PC 端播放走 `media_kit`（libmpv），拿不到字节级吞吐；唯一能采的是代理流量，那只是**一部分**流量，显示出来会误导。**置灰 + 副标题写明「本版本未采集网速」**，而不是给一个点了没反应的开关——`DESIGN.md` 有同类教训："一个点了什么也没有的按钮比没有按钮更糟"。 |
| 3 | 控制栏可见时的强制显示 | 强制显示 **标题 + 分辨率 + 时钟** | **只强制时钟** | PC 顶栏（浮层里的 `AppBar`）已经常驻显示标题与集数，屏显再显示一遍是噪音。分辨率在顶栏没有，但它在控制栏可见时并不比时钟更急。 |
| 4 | 按钮配置的存储格式 | 逗号分隔字符串 | **JSON 数组**（读取时**兼容**逗号分隔字符串） | PC 已有 JSON 设置文件（`settings.json`），再发明一种分隔符格式没有收益。兼容读是为了不让老配置失效。 |
| 5 | 默认隐藏项的播种 | 首次运行**播种**一组默认隐藏项 | **不播种** | PC 端 9 个可配置按钮**没有**默认隐藏项，播种是空操作。写一个恒为空的操作只会让"缺席 = 默认"这条规则变得含糊。 |
| 6 | 可配置按钮数 | **32** 个 | **9** 个 | 只保留 PC 端**有真实实现**的。上游那 32 个里有 23 个在 PC 端没有对应能力（如投屏、倍速记忆、画面旋转等），放进来就是死按钮。27 个被排除的上游 id 及理由逐条写在 `lib/core/player_buttons.dart` 的文档注释里。 |
| 7 | 右键菜单 | **无** | **新增**（六组） | 桌面专属交互。触屏没有右键，所以上游不需要；PC 上右键是"就地设置"的肌肉记忆（PotPlayer / VLC / mpv 都有）。 |
| 8 | 屏显内边距 | `14dp` | `AppSpace.lg` = **16px** | 14 会成为全站第 17 个间距值。`DESIGN.md` 规定间距只能用 `AppSpace` 标度（4/8/12/16/24/32/48），16 是最近的合法值。 |
| 9 | 诊断面板附加列 | 设备 / 系统 / 芯片 / 屏幕 | 运行环境 / 窗口 / 主题 / 本地代理 | PC 上没有"芯片型号""屏幕尺寸"这类字段的可靠来源，**不得伪造**。换成 PC 真实可得的四项。 |

**更正 2（网速）**：上表第 2 条的前提已被证伪，网速**已经实现**。
（这一条本身后又经一道更正：数据源**不是**单一属性 `raw-input-rate`，见本节末尾「已验证，且结论推翻了原实现」。）
上面那行保留「当时如此」的原文，因为它记录了「为什么当初选择置灰而不是给一个空开关」——那条纪律仍然有效。

| 事实 | 当时的写法 | 现在的实际 |
| --- | --- | --- |
| 数据源 | 「media-kit 未暴露吞吐量」 | **双数据源**（见下方「已验证，且结论推翻了原实现」）：**首选** `NativePlayer.getProperty('demuxer-cache-state')` 并从 JSON 串里解析 `raw-input-rate` 字段；**首选解析不到才在同一拍回退** `getProperty('cache-speed')`。单位都是**字节/秒**。`raw-input-rate` **不是属性** |
| 采样 | 「不实现」 | `PlayerController.sampleNetworkRate()`，挂在**既有**的 1 秒屏显循环上，未新增 Timer |
| 覆盖范围 | 「只覆盖代理流量会误导」 | 实测值取自**播放器输入流**本身（限速 ≈136 KB/s 的源读到 `raw-input-rate` = 132086、`cache-speed` = 130786），直连与经代理的字节都计入，故该担忧不成立 |
| 兜底 | — | `parseRawInputRateFromCacheState` 定向正则取字段（键名须完整匹配，`"raw-input-rate-foo"` 不算）；`resolveNetworkRate` 落定回退顺序；`parseByteRate` 把 `null`/空串/`nan`/`inf`/负数 → `null`；`formatByteRate` 把 `null` 显示成 `—`（**不是 0**） |
| 设置项 | 「开关置灰 + 本版本未采集网速」 | 开关**可点**，副标题「取自播放引擎的网络输入速率；取不到时显示 —」（**不再暴露属性名**） |

**当时错在哪（两层，不是一层）**：

1. **以为 media-kit 没有暴露吞吐量。** 实际上 `Player.platform` 在桌面构建里是 `NativePlayer`，
   它暴露 `getProperty(String)`，能读 mpv 的属性；`raw-input-rate` 不在 media-kit 的类型化 API 里，
   所以第一眼看不到，但 `getProperty` 这道逃生门一直在。
2. **而且把 `raw-input-rate` 当成了属性名。** 它其实是 `demuxer-cache-state` 这个 JSON 串里的一个**键**。
   第一版更正只发现了第 1 层，第 2 层是运行时验证之后才发现的（见下节）。

**已验证，且结论推翻了原实现（如实记录）**：

验证方法：用 `dart:ffi` 直接加载 `apps/desktop-flutter/build/windows/x64/libmpv/libmpv-2.dll`，
`mpv_initialize()` 后喂一个**限速到 8192 B / 60ms（≈136 KB/s）的本地 HTTP 源**，逐秒读属性。
（限速让「读数对不对」可判：真实吞吐被钉在已知量级上。）

| 探测 | 实测 | 结论 |
| --- | --- | --- |
| `mpv_get_property('raw-input-rate', MPV_FORMAT_DOUBLE)` | **`rc = -8`** = `MPV_ERROR_PROPERTY_NOT_FOUND`；字符串模式 NULL | **不是属性** |
| `mpv_get_property('cache-speed', MPV_FORMAT_DOUBLE)` | `rc = 0`，`9072 → 72963 → 130786` | 可用，字节/秒，与限速同量级 |
| `mpv_get_property_string('demuxer-cache-state')` | `rc = 0`，JSON 内含 `"raw-input-rate":132086` | 可读，字段在里面 |
| 同上，起播头 ~1 秒 | **NULL** | 缓存建立前无值 |
| `property-list`（827 个属性名） | 含 `cache-speed`/`demuxer-cache-state`/`cache-buffering-state`/`paused-for-cache`，**不含 `raw-input-rate`** | 再次确认不是属性 |

**原实现为什么一直显示 `—`**：`getProperty('raw-input-rate')` 永远 `rc = -8` / 空串 → `null` →
屏显永远 `—`（用户实测反馈「网速还是不显示」）。改成双数据源后此症状消失。

**改后的行为口径**（与 `design/02` §3.6.3/§3.6.5 一致）：起播头约 1 秒 `demuxer-cache-state` 为 NULL、
`cache-speed` 也还没有值，这时**短暂显示 `—` 是正常行为，不是缺陷**；取不到一律 `—`、**不显示 0**；
格式化走 **1000 进制**；只在 `traffic` 开关打开时采样（关着连属性都不读）；
复用既有 1 秒屏显循环，**未新增 Timer**；仅桌面 `NativePlayer` 可用；显示的是「最近一次采样」而非流量计。

**被推翻的旧结论（原文保留）**：

> `raw-input-rate` 只做了编译、单测与渲染链路验证，加上 `libmpv-2.dll` 字符串表里三个属性名
> （`raw-input-rate`、`demuxer-cache-state`、`cache-buffering-state`）存在的确认；**没有**在真实
> libmpv 播放中验证 `getProperty` 的返回值。若不成立，界面显示 `—`：不崩溃、不显示 0。

> **已更正**：把「字符串表里有这个串」当成「它是属性」的推理**无效**——字符串表里有名字只说明
> 它是某个字符串常量（JSON 键名、日志格式）。`rc = -8` 是决定性反证。
> 但「若不成立就显示 `—`」这条兜底**是对的**，而且它当时描述的就是**实际状态**，不是待验证项。

**仍然成立的纪律**：`DESIGN.md` 那条「一个点了什么也没有的按钮比没有按钮更糟」照旧——
所以当初就是置灰而非空壳，能力落地后才解锁。将来若要停用某项，先删能力再置灰。

## 补充：本轮新增的、上游没有的差异

上表之外，本轮还有两条**不属于"与上游的差异"**（因为上游没有对应物），
但同样需要留痕：

| 项 | 处置 | 理由 |
| --- | --- | --- |
| 播放器页**恒定暗色** | `PlayerPage.build` 内包 `buildAppTheme(Brightness.dark)` | 播放器背景是**视频帧**，不是应用底色。用户选的亮色主题作用于应用外壳，不作用于播放器。VLC / mpv / PotPlayer / Netflix 全屏播放器都如此。 |
| 右键菜单用**页内 `Stack` 层**而非 `Overlay` | 见 `design/04` §3 | 截图 harness 取树中第一个 `RepaintBoundary`（`Scaffold` 那层），`Overlay` 浮层**拍不到**。用 `Overlay` 会让"菜单打开"的截图与关闭态逐字节相同——**假证据**。这条决策直接决定了本轮能拿出可复核的菜单截图。 |
