# 12 · 字幕字符集扩展（Big5 / Shift-JIS / EUC-KR）

- 日期：2026-11-15
- 触发：字幕字符集扩展——Big5 / Shift-JIS / EUC-KR
- 相关规格：`docs/phase9/design/02-subtitle-danmaku.md` §1.1、§1.6；`docs/webhtv-pc-design.md` §7.4.1（配置编码边界）

## 1. 目标与边界

**做**：字幕加载支持 Big5、Shift-JIS、EUC-KR 的「声明解码」与「无声明时的证据探测」，
并把实际使用的编码如实写进 `SubtitleDocument.encoding`。

**不做**：

- 配置导入的编码策略不变（仍是 UTF-8 → GBK，§7.4.1）：探测是字幕场景的选择，
  不能顺手改写配置行为；
- 直播源 / EPG / 弹幕仍走原链（同一条解码链，但需要各自的真实样本与验收，
  不在本次范围）；
- 不做「用户手动指定字幕编码」的 UI。

## 2. 为什么不能「谁先不报错就用谁」

样本字节由 CPython 生成（标准实现），再用 Dart 侧的严格 GBK 解码
（`fast_gbk`，`allowMalformed: false`）观察：

| 真实编码 | 样本内容 | 按 GBK 严格解码 | 结论 |
| --- | --- | --- | --- |
| GBK | 中文字幕测试这是第一行… | 正常 | 基准 |
| Big5 | 中文字幕測試這是第一行… | **不报错**，解出 `辊代刚硂琌材…` | 只看异常会漏判 |
| Shift-JIS | テスト用の字幕です… | **不报错**，解出 `僥僗僩梡偺帤…` | 同上 |
| EUC-KR | 한국어 자막 테스트입니다 | **不报错**，解出汉字串 | 同上 |

也就是说：**异常不是判据**。必须比较「解出来的字符是否落在该编码应有的文字范围内」，
再用假名/谚文这类“只可能来自该语言”的字符做决定性证据。

## 3. 实现

| 模块 | 文件 | 内容 |
| --- | --- | --- |
| 解码与探测 | `apps/desktop-flutter/lib/core/legacy_charset.dart`（新） | 别名归一化；严格解码（抛错或出现 U+FFFD 都算失败）；按「脚本纯度」排序，假名/谚文证据优先；探测顺序 GBK → Big5 → Shift-JIS → EUC-KR，纯度差距小于 0.05 视为打平并保留 GBK |

### 3.1 编码源

全部是纯 Dart 实现，Windows/Linux 桌面不需要原生库：

| 编码 | 包 | 许可 |
| --- | --- | --- |
| Big5 | `enough_convert` 1.7.1 | MPL-2.0 |
| Shift-JIS | `charset` 2.0.1 | Apache-2.0 |
| EUC-KR（CP949 表） | `cp949_codec` 1.0.2 | BSD-3-Clause |

**为什么没用 `charset` 的 EUC-KR**：它的表与标准不一致——EUC-KR 的 `0xC7D1`（한）
被它解成 `ꁐ`，整篇韩文字幕会变成错字。CP949 是 EUC-KR 的超集，
`cp949_codec` 对同一字节解出正确的 `한`。

### 3.2 探测规则（可复核）

1. 严格解码：抛错或结果含 U+FFFD → 该候选不适用；
2. 每条候选算「脚本纯度」= 1 − （该编码不该出现的字符数 / 非 ASCII 字符数）：
   - 日文：汉字、假名合法，谚文异常；
   - 韩文：谚文合法，汉字（hanja）与假名异常；
   - GBK：**假名合法**（GBK 的 A4/A5 行含 176 个假名，带日文歌词的简体字幕很常见），
     谚文异常；
   - Big5：假名、谚文都异常；
   - 全角标点、全角符号、通用标点与西文重音不计异常；半角片假名按乱码计，
     只有“整段都是它”时单独放行（见边界 #3）；
3. 取纯度最高者；与最高分差距 ≤ 0.05 的候选算打平，打平时先看证据字符：
   - 全角假名 ≥ 3 且占比 ≥ 0.3、汉字占比 ≤ 0.7 → Shift-JIS；
   - 谚文 ≥ 3 且占比 ≥ 0.3、汉字占比 ≤ 0.25、**非 ASCII 字符总数 ≥ 8**，且**每一行
     含谚文的文本都有空格分词** → EUC-KR（短文本上两种编码对称，见边界 #2；中文被
     CP949 误解出的谚文整行没有空格，歌词式重复台词靠这条判掉）；
   - 否则按 GBK → Big5 → Shift-JIS → EUC-KR 的顺序取第一个；
4. 一个候选都不“像话”（乱码占比 > 0.6）时，只有一种例外被接受：Shift-JIS 解出
   **整段半角片假名**（可夹 ASCII），且它是唯一能解的候选；其余情况返回 null，
   由调用方报可定位错误——不把随机字节硬猜成“能读的文本”。

## 5. 已知边界（如实记录）

1. **纯汉字的日文**（例如只有漢字、没有假名的行）与中文在字节证据上无法区分，会按 GBK 解；
   这是编码事实层面的不可判定，不是实现取舍。
2. **短文本没有足够证据**（实测：3–5 个汉字就可能翻车）。短中文的 GBK 字节在 CP949
   下解成纯谚文，短韩文的字节在 GBK 下解成纯汉字——两边纯度都是 1.0，对极短文本是
   真不可判定。按“TVBox 生态以简体中文源为主”与“打平按 GBK”，用**非 ASCII 字符总数
   < 8 不采信韩文证据**兜底，代价与收益（第二轮审查实测）：
   ```text
   minTotal  中文短句错   韩文短句错   已提交韩文语料错   日文错
      0        20/178      23/53         0/97            0/235
      8         0/178      51/53         9/97            0/235   ← 采用
   ```
   即：**短句优先中文**。一条韩文/繁体短句（如“안녕”“謝謝”）可能落到 GBK 或报错；
   多行韩文字幕文件不受影响（整份文件一起判定，样本 349 条中文/日/韩语料 0 失败）。
   另有“歌词式”形态：同一句短台词重复多行时总量会跨过门槛，按韩文“按词空格分词”
   再判一次——被误解成谚文的中文行内没有空格，因此仍留在 GBK（实测 24 条多 cue
   简体字幕 0 失败；代价是“每行只有一个韩文单词且不带空格”的字幕会落 GBK）。
3. **半角片假名**只作为“唯一能解的候选”放行（整段 `ﾃｽﾄ…` 的旧日文样本）。
   有可读的中文候选时不会被它抢走：把半角片假名当假名证据会让几乎所有中文标点都被
   Shift-JIS 解成 `｡｡｣ｬｰ｡`，所以它不算“日文证据”。
4. **CP949 的标签**：解码用 CP949 表，但记录为 `euc_kr`；CP949 扩展区字符能解出来，
   语义上仍标 EUC-KR。
5. **声明 charset 能干净解码时不探测**：声明是事实，按它解；只有解出 U+FFFD（声明与
   字节不符）才改走证据探测，探测也无解则保留声明路径的既有容错文本并如实记录编码。
6. **配置与其它调用方不受影响**：`allowLegacyCjk` 默认 false，声明阶段也不认这三种
   编码；`test/core_protocol_test.dart` 断言了「关闭时 Big5 字节仍按 GBK 解」与
   「配置声明 big5 仍报 `configDecode`」两条边界。

## 6. 独立审查发现与修复

第一版实现自测全绿后，独立审查（另一个 agent，只读、自建 736 条对抗语料）指出了
两个真问题；用本仓语料复现后修复，并补了对应样本：

| 编号 | 问题 | 复现 | 修复 |
| --- | --- | --- | --- |
| C1 | GBK 的假名被当成“异常字符”，一份含日文歌词的简体字幕被判给 Big5（相对改动前是回归） | `この曲は本当にいいね、我喜欢这首歌`（GBK）→ 解出 `仇及⑻反掛絞卞中中友﹜…` | GBK 候选的异常字符改为「乱码 + 谚文」，假名算合法 |
| C2 | 日文汉字占比上限 0.4 太窄，单条日文字幕失去日文证据，被 CP949 解成“纯谚文”抢走 | `明日は学校に行きます` → `뼻볷궼둾뛝…` | 汉字上限放宽到 0.7、假名/谚文证据比例回到 0.3，并让日文判定先于韩文 |
| C3 | 文档承诺“不写入 U+FFFD”，但声明路径确实会写 | 声明 utf-8 + 非 UTF-8 字节 | 声明解出 U+FFFD 时改走证据探测；文档收窄为“探测路径严格、探测无解才沿用声明容错” |
| I1 | 认识的名字解不出来时仍报“不支持的字符集”，自相矛盾 | `declaredCharset: 'big5'` + 非法字节 | 拆成「按声明的 big5 无法解码内容」与「不支持的字符集」两种文案 |
| I2 | 配置导入开始接受 Big5 声明，与“配置策略不变”矛盾 | `decodeConfigText(bytes, declaredCharset: 'big5')` 曾不再抛错 | 三种编码整体由 `allowLegacyCjk` 开关控制；配置路径的错误分类与判定与改动前一致，仅文案统一为「不支持的字符集」（原为「不支持的配置字符集」） |
| I3 | 新增测试恰好绕开 C1/C2 的场景 | 原 14 条样本全是“干净”句子 | 样本扩到 21 条，加入 GBK+假名、汉字占比高的日文单句、整段半角片假名（第二轮补 3 条短中文，第三轮补 1 条歌词式多 cue，共 25 条） |

另修 Minor：声明别名归一化后再记录（`cp950` → `big5`，GBK 家族保留 `gb2312`/
`gb18030` 原样）、去掉不可达分支、半角片假名的边界描述改为实际行为。审查提到的
“证据文档引用的日志不存在”不成立：`.local/full-test-charset.log` 存在（1.78 MB）。

### 6.1 第二轮复核（新增一条阻断问题）

第二轮的独立复核用 1067 条语料发现：**短中文句被判成韩文**，是相对改动前的真实回归
（`对不起` 的 GBK 字节在 CP949 下解成 `뚤꼇폅`，端到端 `SubtitleService` 记录
`encoding=euc_kr`，整篇乱码）。用本仓语料复现：短句语料 24 条里 7 条中文被判成韩文。

| 编号 | 问题 | 处理 |
| --- | --- | --- |
| RC（阻断） | 短中文 → 韩文（见边界 #2 的对称性分析） | 韩文证据增加「非 ASCII 字符总数 ≥ 8」门槛；短句优先中文。中文短句 20/178 → 0/178，代价是短韩文 51/53 落到 GBK（已写入边界 #2）。另补 3 条短中文样本（`对不起`/`你吃饭了吗`/`好厉害`）与一条具名回归用例 |
| I-1 | 边界 #2 与实测不符（说“整句不受影响”，实测 3–5 汉字就翻车） | 按实测数据重写，附阈值权衡表 |
| I-2 | 别名归一化把 GBK 家族也改了（`gb2312`/gb18030/cp936 被记成 gbk） | 只归一化三种新编码；GBK 家族保留声明原样 |
| I-3 | “乱码最少”兜底把硬错误变成静默乱码 | 取消该兜底，只保留“整段半角片假名且是唯一可解候选”的窄例外；其余返回 null 报错 |
| M-b/M-c/M-d | 半角片假名措辞、格式、尾返回 | 边界 #3 改为实际行为；尾返回标注为防御分支 |

### 6.2 第三轮：阈值收紧 + 我自己复核出的两个新问题

第三轮 reviewer 修掉了我复核出的三处（半角例外缺“唯一候选”守卫、GBK 家族标签无入库
断言、乱码阈值过宽），判定可合并。我没有直接采信，自己复测后另发现两处：

| 编号 | 问题 | 处理 |
| --- | --- | --- |
| L1 | 乱码阈值 `junkRatio ≤ 0.6` 过宽：随机字节里 63 条被 Shift-JIS 解成混合乱码却当成字幕接受 | reviewer 改为 `≤ 0.2` + 至少一个汉字/假名/谚文，并把箭头/框线/几何/杂项符号收进“合法标点”（否则 `★ 我等你 ★` 这类真实字幕会被误伤）。实测：混合乱码 63 → **0** |
| L2 | 歌词式多 cue 简体字幕（同一句短台词重复多行）仍被判成韩文 | 我接手加“韩文按词空格分词”判据：每行含谚文的文本必须有空格；实测多 cue 语料 4/24 → **0/24**，补固定样本与具名回归用例 |

随机字节最终实测（4000 条，种子 20261115，基线口径 = 改动前“UTF-8 失败后只试 GBK”），
与 reviewer 报的 89 不同是因为它把“全部被接受”算进去了，我按“改动前会报错”算：

```text
改动前报错、现在被接受：56 条 —— 全部是 Shift-JIS 解出的整段半角片假名，混合乱码 0 条
改动前解出高乱码文本、现在报错：64 条（宁可报错，不硬猜）
```

半角例外的守卫也复核过：`[0xA2,0xBB]`（四个编码都能严格解码、但没有一个是文本）现在
返回 null；`[0xA1]`（唯一可解）仍按 Shift-JIS 放行。

修复后回归：14 条对抗样本 0 失败；大语料 349 条（300 简体 + 20 日 + 15 韩 + 15 繁）
0 失败；短句语料 24 条仍有 8 条不通过，全部落在已声明的边界（2 条短繁体、6 条短韩文）。
