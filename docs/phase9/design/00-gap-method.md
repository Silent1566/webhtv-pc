# 00 · 差距对比方法与判定口径

- 阶段：Phase 9（差距分析）
- 上游：`docs/phase9/README.md`
- 基准：安卓 `F:/Workspace/webtv2/webhtv` @ `77e2fbefdc`；PC `81c398c`

---

## 1. 为什么要先定口径

Phase 4–8 的经验是：**「看起来有」和「真的能用」是两件事**。

- Phase 4 的发布包里，TMDB 设置页藏在详情页状态条后面，用户以为功能没编进去；
- Phase 8 之前，`PlayerButtonSetting` 的 32 个按钮里有 27 个在 PC 端没有实现，`core/player_buttons.dart` 因此把它们整体排除，而不是放上去装样子。

所以本阶段的判定不看「字段是否存在」「按钮是否存在」，只看三件事：**入口可达、行为可观测、失败可诊断**。

---

## 2. 判定三档

| 档 | 定义 | 反例（必须判为缺失） |
| --- | --- | --- |
| 已对齐 | UI 有可达入口；服务层有真实实现；有单元或集成测试锁定行为 | —— |
| 部分对齐 | 只有数据层或只有 UI 之一；或只覆盖了主路径 | `ads`/`hlsRules` 有字段但没有消费点；字幕服务能读本地文件但没有选择入口 |
| 缺失 | 无实现；或实现只覆盖不可用形态 | 「点了没反应」的按钮；只解析不生效的配置；靠注释声明「已支持」 |

**特例**：平台不适用（TV 焦点、手势、dex 站源）单独归入「不迁移」，不得混进「缺失」来抬高完成度，也不得混进「已对齐」来掩盖。

---

## 3. 证据要求

每个判定必须能指到代码，而不是指到文档：

- 安卓依据：`android/<仓库相对路径>`，文件或目录均可；目录用于「这一整块能力」的引用。
- PC 现状：`apps/desktop-flutter/<仓库相对路径>`；新模块写 `PLANNED apps/desktop-flutter/...`。
- 行为类结论（例如「搜索按配置顺序」）必须能指到具体函数或常量，不能只写「没有」。
- 引用路径由 `tools/phase9/verify_gap_matrix.py` 校验存在性（G9.2/G9.4）。

---

## 4. 覆盖基线（G9.3）

安卓仓库的**用户可见面**按四类清点，任何一类出现「没有归属」都算分析不完整：

| 类别 | 数量 | 来源 | 覆盖方式 |
| --- | --- | --- | --- |
| manifest 屏幕（Activity） | 43 | 四个 `AndroidManifest.xml` 的 `<activity>` | 每个屏幕在 `design/05` 映射到「已对齐」或某个 P/N 编号 |
| 对话框 | 84 | `app/src/main/java/.../ui/dialog/*.java` | 同上 |
| 设置 Fragment | 9 | `app/src/*/java/.../ui/fragment/Setting*Fragment.java` | 同上 |
| 顶层模块 | 34 | `app/src/main/java/com/fongmi/android/tv/*/` | 同上 |

PC 侧基线（用于「已对齐」判定）：`lib` 108 个源文件、18 个页面、115 个单测文件、31 个集成测试文件。

数量会随安卓仓库演进而变；脚本以运行时清点结果为准，**不写死数字**。文档里的数字只作当前快照。

> 注意：清点包含 flavor 源集（`mobile`/`leanback`）。同一个屏幕可能在两个 flavor 有不同实现，映射只记一次，归属相同。

## 5. 优先级规则

| 档 | 判定依据 |
| --- | --- |
| P0 | 缺失会打断「打开就能看」的日常闭环；桌面无平台障碍；不需要新依赖 |
| P1 | 决定真实配置的可用率或可诊断性；有明确的上游协议/规则可对齐 |
| P2 | 内容形态与跨设备协同；依赖安卓契约或新的数据模型 |
| P3 | 需要新的进程/权限模型或第三方依赖，必须先 ADR |

同档内按「用户可感知频率 × 失败代价」排序，不按实现难度排序。

---

## 6. 与既有阶段的关系

- Phase 0–8 已完成的能力**不重新实现**，只在矩阵里登记为「已对齐」。
- 本阶段不修改 `docs/phase0`–`phase8` 的任何验收结论。
- 若某项在旧设计文档里被列为「后置/完整版必须」（例如 `docs/webhtv-pc-design.md` §7.2 的 `doh`/`proxy`/`hosts`/`rules`/`hlsRules`/`groupRules`/`ads`），本阶段按实际代码重新判定，不因「设计里写了」就算已实现。

---

## 7. 已知局限

1. **真实源不可复现**：矩阵只承诺 fixture 可复现；真实站点行为由用户配置决定，验收时必须区分「协议失败 / 站点失效 / 地区限制 / 播放器失败」。
2. **安卓仓库会演进**：基准固定到 commit；升级基准时必须重跑 G9.2/G9.3，并更新映射表。
3. **对话框粒度**：84 个对话框里有基类（`BaseAlertDialog` 等），映射到「基础设施」而不是具体缺口；这不算漏项，但必须在映射表里显式写出来。
4. **不可见能力**：安卓的保活、崩溃恢复、电池适配等没有 UI 入口，只能从模块与文档推断；本阶段按「有用户可见后果」才收进矩阵。
